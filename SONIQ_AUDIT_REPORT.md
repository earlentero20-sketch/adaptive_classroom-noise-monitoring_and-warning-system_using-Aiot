# SONIQ Repository Audit

**Audit date:** 2026-11-09 (Asia/Manila)  
**Scope:** Repository files present in the working tree, configuration, model metadata, and available command-line tooling. No live database, backend process, browser, or physical device was available for this audit.

## Executive summary

This is an existing multi-component prototype, not a missing or replacement project. It contains a standard-library Python HTTP backend, PostgreSQL event storage and migration, a static HTML/CSS/JavaScript dashboard, an ESP32 Arduino sketch, an ML training/inference pipeline, datasets, and three serialized experimental model artifacts. The code deliberately prevents warnings without valid configuration and does not claim that local RMS is dB SPL.

The software components are reasonably well separated, but the complete ESP32-to-audio-model-to-event workflow is not integrated. The ESP32 posts placeholder classification and sound fields to `/api/v1/events`; it does not transmit microphone audio to `/api/v1/classify`. It also targets a LAN IP while the documented backend binds to loopback, so the current firmware destination is incompatible with the current local-only server binding. The dashboard uses real backend responses but cannot show an ML classification until an artifact is configured and the endpoint succeeds.

Existing model files were found at:

- `ml/artifacts/experimental-demo-local/experimental_model.joblib`
- `ml/artifacts/experimental-demo-school-20261020/experimental_model.joblib`
- `ml/artifacts/expanded-local-demo-20261020/experimental_model.joblib`

All available run metadata identifies the artifacts as `experimental_full_fit_no_held_out_evaluation`. The expanded artifact is marked `local_only_expanded_demo_unreviewed`; the other metadata marks the dataset review as not formally cleared. They have no held-out evaluation metrics. These files are preserved, but they are not evidence of an approved, evaluated, demonstration-ready classifier. Model deserialization and real WAV inference could not be run in this environment.

## Endpoint and event workflow audit

- `GET /health` reports process status separately from warning configuration readiness.
- `GET /api/v1/events` retrieves persisted events with strict pagination handling and structured storage errors.
- `POST /api/v1/events` validates the event contract, applies the backend warning policy, and stores the resulting event when the repository is available.
- `POST /api/v1/classify` accepts a complete PCM WAV upload and uses the configured local artifact. This path returns classification only; it does not create an event or evaluate the warning policy.
- Dashboard reads the same backend endpoints and shows explicit unknown/unavailable states instead of synthesizing readings.
- Firmware posts events without a model label or sound level. It does not implement the separately proposed serial/HTTP audio transport.
- No migration or API schema change was made during the audit.

## Prioritized repair plan

1. Resolve the abnormal staged-deletion/untracked Git state with the repository owner before staging, committing, or cleaning anything.
2. Establish a supported local Python environment and install only reviewed dependencies; do not reuse the copied virtualenv. Then run the existing backend and ML unit suites and dashboard tests.
3. Have the model/data owners confirm whether an existing experimental artifact may be used for a clearly labeled demo. Verify its actual load and WAV inference in the approved environment. Do not retrain or replace it as part of this audit.
4. Configure a project-approved PostgreSQL instance and warning values through environment variables, apply the existing migration only after database-owner review, and exercise health, event insert/list, and classify behavior against that local setup.
5. Decide and approve the firmware/backend transport and network exposure. Current loopback binding cannot accept the sketch's LAN request; current sketch sends no audio and no measured dB SPL. Keep the buzzer disabled until the complete policy and physical safety path is approved and tested.
6. Perform browser/dashboard checks and physical ESP32/microphone/LED/buzzer tests on the actual target hardware. Record evidence and limitations.

No source implementation was changed during this audit because the available blockers concern environment, data/model approval, transport design, and hardware verification; changing APIs, model/data, or device behavior without those decisions would risk existing components.
