# Model Selection and Data Readiness (Provisional)

**Scope:** exactly `Teacher Discussion` and `Student Conversation`. This is a
planning assessment; no dataset has been downloaded or approved and no model
has been trained.

## Candidate approaches

| Approach | Training and compute | Inference/deployment | Explainability and fit | Assessment |
|---|---|---|---|---|
| MFCC or log-mel summary features + regularized logistic regression / linear SVM | Lowest-cost candidate; needs labeled, recording-diverse examples and a fixed feature pipeline. CPU training and inference are modest. | Straightforward on a host/backend. It can later be ported if the feature implementation and runtime are reproduced. | Feature weights are inspectable, but role errors remain hard to explain. Aggregated features can lose turn-taking/context. | **Recommended first baseline for host-side experimentation**, once authorized data and feature dependencies are available. It is the smallest useful comparison, not a committed production model. |
| Small log-mel 2D CNN | More training/validation data and tuning than a linear baseline; more compute, though still feasible on a development host. | Host inference is practical in principle; deployment requires a chosen runtime and measured latency. | Learns richer time-frequency patterns but is less transparent and can overfit a small number of recording sessions. | Keep as a second-stage challenger only if the linear model and data volume justify it. |
| Tiny quantized CNN + TFLite Micro on ESP32 | Requires embedded-oriented training, quantization-aware checks, a matching fixed-point frontend, and target-specific memory profiling. | On-device inference can avoid sending raw audio and reduce network dependence, but feasibility depends on exact ESP32, microphone, memory, and latency. TensorFlow Lite Micro's official Micro Speech example demonstrates a <20 kB keyword model with 16 kHz mono PCM and a specific spectrogram frontend; that is evidence of a feasible pattern, not evidence this role-classification model will fit or work. | Lowest observability in the system and most deployment coupling. Distinguishing classroom roles is harder than recognizing two isolated keywords. | **Do not select yet.** Keep it as an option if hardware/privacy requirements require local inference and the target is confirmed. |

Host-side experimentation is the practical recommendation now: it matches the current Python evaluation pipeline and avoids assuming ESP32 capability. This does not decide whether the eventual service is the backend or another host. No runtime dependency is currently installed, so implementing and measuring the baseline still requires an approved dependency choice/install phase.

## Pipeline review before training

- **Preprocessing:** the current standard-library decoder supports PCM WAV and explicit channel mix, window length, crop strategy, normalization, and linear interpolation. Linear interpolation is not an anti-aliasing resampler, especially for downsampling. Channel averaging can cancel phase-opposed content. The chosen sample rate/window/channel policy must match the microphone and model frontend and be validated on authorized recordings. Formats other than WAV are reported, not converted.
- **Splits:** groups use `(source_id, original_recording_id)`, which prevents sibling clips from crossing partitions only if curators assign stable, shared IDs across every derivative/source export. The hash split is deterministic but not stratified. Review class and independent-group coverage before fit; `summarize_split_readiness` now reports missing labels and low group coverage. Its readiness flag is a minimum diagnostic, not statistical adequacy.
- **Metadata/labels:** the intake now requires source/license references, approval status and review reference, classroom consent/privacy review references, and annotation status/reference. Ambiguous, pending, or rejected annotations are excluded with explicit issues. These fields are gates and audit pointers; humans still have to inspect the underlying terms, consent, and review records. Exact two-class labels and path/ID uniqueness are checked.
- **Reproducibility:** manifests include ordered clip metadata, file hashes, audio properties, preprocessing, and split assignments. They currently do not record split seed/fractions, code revision, feature extractor version, or environment lock. Add these to a run record before real training.
- **Artifact management:** no trained artifact exists. When one is authorized, store it outside Git or in an approved artifact location with model hash, class order, preprocessing/frontend version, training manifest hash, code revision, seed, dependency versions, and evaluation report. Never include private audio or identifying metadata in the artifact package. Review whether model weights themselves may encode restricted data before sharing.
- **Evaluation:** use the held-out groups once. Report per-class precision/recall/F1, confusion matrix, macro-F1, class/group counts, source limitations, and a separate approved classroom test if available. Do not use fixture outputs as model results.

## Smallest defensible next experiment

After approvals, implement one fixed log-mel or MFCC extractor and compare a regularized logistic regression or linear SVM with a majority-class reference that always predicts the most common training class. Use the same recording-grouped split and fixed preprocessing for both; determine the majority class from training only. Report per-class precision, recall, F1, confusion matrix, and macro-F1 for both systems only after a real approved-data run. This gives a simple host-side baseline with modest compute and an understandable feature-weight view. It is only defensible if each class has multiple independent recording sessions in train, validation, and test; the pipeline's two-groups-per-class diagnostic is a floor for catching obvious gaps, not a guarantee of statistical power. Include an overlap/ambiguous review set outside the two training labels and report its handling separately.

Record canonical run metadata with split method/seed/proportions,
preprocessing configuration, feature extractor name/version/configuration,
dataset-manifest hash, and code revision when available. The helper is in
`ml/experiment.py`. Store model artifacts and full reports in an approved
location outside Git, and bind each artifact to this run record.

Before the experiment begins, the team needs:

1. A written decision on host/backend versus ESP32 inference for the first prototype, or explicit agreement that this baseline is host-only research pending deployment selection.
2. Exact microphone/device model, capture encoding, sample rate, channel count, gain path, and expected clip/window duration.
3. One dataset or recording protocol with documented rights for ML training/evaluation, school permissions, participant consent, privacy safeguards, retention/deletion rules, and an approved storage location.
4. Stable `source_id` and original-recording IDs, two-class annotation rules, an overlap/ambiguous review state, and class/group counts sufficient for grouped partitions.
5. Team agreement on the output contract, confidence semantics, and how classification combines with separately measured/calibrated sound level. Student Conversation alone must not imply a warning.
6. Approval for the feature/model dependencies and an artifact location. No dependencies were installed during this phase.
